# 验收、修复与完成口径

## 1. 从功能清单导出验证，而不是从现有测试倒推范围

每个本轮纳入项映射到行为合同、实现入口/模块、至少一个合适的 TC 及实际证据。检查子行为和跨功能依赖；不能因为测试都绿了，就推定没写入测试的功能也已完成。

分别回答：是否实现？是否执行验证？是否通过？目标基线是否实测？所有四项都有证据边界。延期和排除保留原因与原始清单，不纳入通过数。

## 2. 分层验证

| 层次 | 应证明什么 | 不能替代什么 |
| --- | --- | --- |
| 静态与构建 | 当前配置可编译，类型/格式/既有 lint 及相关检查通过 | UI、输出与运行期兼容 |
| 模型/单元 | 状态、输入边界、历史、引用、错误分支 | 真实系统 API 与设备 |
| 集成 | 文件、持久化、编解码、平台接口或网络的实际链路 | 全部用户操作与第三方平台 |
| UI 主流程 | 可见界面的点击、输入、焦点、开关、弹窗和完成/错误反馈 | 后台输出内容正确 |
| 输出与恢复 | 内容真实可用、重开一致、取消/错误不会假成功、原件保留 | 其他机器、长时间与所有组合 |
| 实际交付物 | 解压/安装后启动与关键功能、相对路径和依赖完整 | 全新环境，除非确在新环境测过 |

选择已有且适合的工具；新增测试框架/浏览器/工具仍须按安装规则批准。Web 与桌面的 UI 验证分别使用其可用工具，遵守当前工具说明，不把 DOM/组件测试当作真实桌面验收。

## 3. 对本轮改动有意义的回归

优先验证主闭环、受影响的依赖和历史缺陷。关注以下常见遗漏，按产品选取：

- 新增内容能否保存/重开，撤销/重做后是否一致？
- 开启功能后能否关闭，关闭后的效果和资源是否立即清除？
- 改变范围、切换来源、关闭窗口及重启是否残留旧状态？
- 错误、取消、空输入、无权限、资源占用时是否明确失败/恢复，是否产生假完成记录？
- 用户是否能找到入口，缩放或窗口变小时关键控件是否可见？

不要给所有小改动强制重跑无关的大型套件。受影响检查通过后，仅在新失败、改动或未消除风险出现时追加测试；但最后的完整功能清单核对不能省略。

## 4. 媒体、硬件与网络产品的特别检查

录屏/音频/摄像头产品要分清捕获、合成、时钟、编码、封装、播放与资源收尾；一个 API 可用不代表整条链路通过。仅在已授权的设备和声音范围内测试，不自动调系统音量或隐私权限。

- 用短时原创测试画面，实际检查输出参数、完整解码、画面变化、叠加内容和播放。FFprobe 等只在可用/获准安装时使用。
- 声音有轨道不等于录到了正确声音；合成音轨、静音、回环、真人讲话和主观听感分别记录。用户不方便说话时保留未验，不编造人声验证。
- 摄像头初始化成功但黑屏，先区分物理开关、权限、占用与真实帧；需要用户动作就具体说明。演示素材不使用私人摄像头影像。
- 模拟输入和真实设备区分；一个 GPU/设备通过不代表所有设备兼容。回环推流通过也不代表公网直播平台通过。

其他产品采用同样原则：导出文件要实际打开，保存要实际重开，网页离线、系统权限与部署环境要按承诺分别验证。

## 5. 缺陷闭环与完成报告

先保存失败证据，再定位实现错误、规格缺口或平台差异。修改自主设计时同步合同和用例，但不能为了通过而弱化用户要求。用相同复现路径和相关回归验证修复；未实际复验的修复只能记为“待验证”。

最终报告列出：候选/本轮范围与各状态数量、逐项对应、真实执行环境与版本、失败和未执行项、差异/限制及下一步。禁止将跳过、阻塞或人工待验计为通过。

只有纳入项实现完毕且其必要验收全部实际通过，才说“本轮约定范围完成”。若有任一必要项目未执行，报告“实现完成，部分验收待执行”。不要把这一结论扩大成“目标产品完全一致”或无依据的百分比。

用户要求分发时，验证最终压缩包/安装包而非只测开发目录；严格锁定/重新还原项目依赖与发布依赖，确认从源码可构建。区分运行时和开发环境，保留第三方许可和来源说明；无需分发时不额外创建仓库或发布版本。
